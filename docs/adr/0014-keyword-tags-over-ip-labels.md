# ADR-0014: Twitterコーパス由来のキーワードをIPラベルではなく「タグ」として扱う

- **Status**: Accepted
- **Date**: 2026-05-02

## 背景

ADR-0013でTwitterコーパスのTF-IDF/グラフクラスタリングによるIP同定を検証した。
クラスタリング自体は機能したが、実運用に向けて根本的な問題が浮上した。

**IPという概念の粒度が一様でない。**

- `イカゲーム` クラスタ → 単一IP、明確
- `NAMJATOWN` クラスタ → 会場名が引力（A3!・あんスタ・グノーシアが共起）
- `ReoNa` クラスタ → 人物名
- `ウルトラマン 2` → ip_registry側の命名が揺れている

「このクラスタをどのIPに対応させるか」という判定が自明でなく、
「正確なIP同定」として使うには別の分類レイヤーが必要になる。

## 決定

Twitterコーパスから抽出したキーワードを **IPラベルではなく「タグ」** として扱う。

タグは以下の性質を持つ：

- IP名・チーム名・キャラ名・会場名・公演形態など、種別を問わず等価に扱う
- 「このイベントを検索・発見するために使えるキーワード」という定義
- ip_registryとの1対1マッピングは要求しない

## 根拠

### 仮定は正しいがゴールが変わった

「同じキーワードが出るイベントは同じ文脈に属する」という仮定はクラスタリング結果から正しいと確認できた。
ただしその「文脈」がIPとは限らない——会場・人物・公演シリーズも含まれる。

これらを「IPではないのでノイズ」と捨てるより、
**タグとして等価に扱うほうが情報損失なく活用できる。**

NAMJATOWNクラスタを例にとると：
- IP同定の文脈: ノイズ（会場は IPではない）
- タグの文脈: 有用（「NAMJATOWN系コラボイベント」を探したいユーザーに刺さる）

### 逆引きが機能する

`event_ip_link` に紐付けが入っているIPに対して、タグ辞書の逆引きが実用レベルで動作することを確認した。

```sql
SELECT ek.keyword, COUNT(DISTINCT ek.event_id) as cnt, AVG(ek.weight) as tf
FROM event_keywords ek
JOIN event_ip_link il ON ek.event_id = il.event_id
JOIN ip_registry ip ON il.ip_id = ip.ip_id
WHERE ip.display_name = 'ハイキュー!!'
GROUP BY ek.keyword ORDER BY cnt DESC
```

結果例（ハイキュー!!）:
```
ハイキュー!! 49件  梟谷学園 30件  音駒 20件  烏野 20件  稲荷崎 20件  影山 5件 ...
```

IP名だけでなく、チーム名・キャラ名まで自然に辞書化される。

### 使い道

| 方向 | 用途 |
|------|------|
| イベント → タグ | 検索インデックス。タグ付きイベントを横断検索できる |
| タグ → イベント | 「このタグのイベント一覧」 |
| IP → タグ辞書 | ip_registryに紐付いたイベントのキーワードを集約 → 新規イベントの自動タグ推定に使える |

## トレードオフ

**採用の理由:**
- IP同定の「正解」を定義する困難さを回避できる
- 会場名・人物名・公演形態も含め、ユーザーの検索意図に応える
- タグ辞書（IP → keywords）は自動生成でき、新規イベントの推定精度向上に使える

**リスク・制約:**
- タグ品質はツイート数に依存する（ツイートが少ないイベントはタグが貧弱）
- `--min-tf 0.1` フィルタを外すと声優・アーティスト経由のノイズが混入する
- NAMJATOWN のような会場タグと IP タグが混在するため、タグ種別の属性管理が将来必要になる可能性がある

## 影響するコンポーネント

- `event_keywords` テーブル: タグの実体（変更なし、解釈が変わる）
- `ip_keyword_analysis.py`: クラスタリング結果の読み方がIP同定からタグ生成に変わる
- `ip-link-agent` CronJob: 精度問題の深刻度が下がる（完全なIP同定でなくてよい）
- 将来的なフロントエンド: タグ検索UIが主要インターフェースになりうる
